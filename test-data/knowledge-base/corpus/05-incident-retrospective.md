# 2027-06-21 知识引用异常事故复盘

> 事件编号 NP-INC-0621，状态：已关闭。本文为虚构的 RAGFlow 检索测试资料。

## 事件摘要

2027 年 6 月 21 日 10:14，华东门店开始报告“回答正文基本正常，但引用卡片为空或指向旧公告”。
问答入口和登录均可使用，没有发现跨租户访问。10:22 值班工程师按 P1 接管，11:49 确认用户路径
恢复，实际影响 87 分钟。受影响范围为杭州与苏州共 12 家已验收门店，宁波尚未上线因此未受影响。

事件被定为 P1 而不是 P0：核心入口仍可用、数据可以从源文档重建、没有确认泄漏或不可逆损坏；
但引用链路大面积失败，已经达到运维手册的严重降级条件。87 分钟小于 P1 的 4 小时服务恢复目标，
因此恢复时限达标；这不代表事故处理质量没有改进空间。

## 时间线

10:07，知识运营人员发布“夏季陈列规范”新版，文档解析成功。10:12，自动任务把一个仅用于预演
的数据集别名写入生产检索配置。10:14，首个门店问题命中预演索引，其中包含过期片段但没有当前
文档的外部引用。10:18，引用为空率告警超过 20%，但告警只发到低优先级频道。

10:22，值班工程师收到门店升级并建立 P1 工单。10:31，团队确认 MySQL 会话、百炼生成和 RAGFlow
API 都健康。10:43，通过请求 ID 关联发现检索结果来自错误数据集。10:51，有人提出临时关闭引用
展示以恢复“视觉正常”，事件负责人否决该方案，因为它会掩盖可追溯性缺失。

11:02，团队停止错误别名的继续发布；11:16 回滚到上一版索引映射；11:31 重新发布新版文档；
11:42 用正式页面验证已知事实与引用；11:49 华东 12 家门店抽样全部通过，状态改为已恢复。随后
继续观察 30 分钟，于 12:19 转为已关闭。

## 根因与促成因素

直接根因是索引发布任务接受了未区分环境的逻辑别名。预演和生产数据集都通过健康检查，但检查只
验证“数据集存在”，没有验证租户、环境和文档版本三者一致。发布任务缺少生产命名约束，也没有
要求调用者提交期望的数据集 ID。

促成因素包括：引用为空率告警没有进入 P1 频道；上线检查只问了一个宽泛问题，正文看似合理但没
核对引用；预演数据保留时间过长；值班手册虽禁止隐藏引用，但页面没有把引用质量作为独立健康项。
百炼模型和 RAGFlow 服务本身没有故障，重启二者不会解决该问题。

## 恢复验证

团队使用三个问题验证恢复。第一个询问夏季陈列生效日期，必须命中新版公告；第二个对比两个区域
例外，需要同时引用两份文档；第三个询问资料中不存在的奖金金额，必须回答无法确认。三个问题都
从正式页面发出，引用的知识库 ID、文档 ID 和租户归属均正确。

团队没有采用“关闭引用展示”的临时方案，也没有直接修改数据库中的消息状态。最终恢复动作是
回滚错误索引映射、重新发布正确文档并经用户入口复验。历史中 23 条带错误引用的回答保留用于审计，
页面提示用户重新提问，没有静默改写已发送内容。

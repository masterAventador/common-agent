北极星计划容量、性能与模型成本计划
文档编号 NP-CAP-2027-05，正式版 1.2。本文为虚构的容量检索测试资料。

一、目标负载

首批 18 家门店预计有 240 名周活跃用户，工作日 10:00 至 11:00 和 16:00 至 17:00 为高峰。高峰
普通问答预计每分钟 90 次，设计软配额为单租户每分钟 120 次，短时突发允许 150 次持续 30 秒。
超过软配额返回可重试限流，不排队到用户无法判断是否发送成功。

预计同时存在 48 个流式会话，其中约 12 个会执行知识检索。这里的 48 是全租户目标并发，不是每
分钟请求数。工作流 AI 节点的单租户软配额是每分钟 30 次，和普通问答的 120 次分别计数，避免批量
工作流挤占交互会话。

二、延迟预算

普通无知识问答首字 P95 目标为 1.8 秒，完整回复 P95 为 3.0 秒；带知识检索的完整回复 P95 为
3.5 秒；跨三份以上文档的复杂问题观察目标为 5.0 秒。试点验收得到常规问答 P95 2.8 秒，满足
3.5 秒门槛，但不能据此承诺所有复杂问题都低于 3 秒。

一次带知识问答的预算拆分为：平台校验 100 毫秒、RAGFlow 检索与重排 900 毫秒、模型首字 1.5 秒、
流式传输和投影 1 秒。各段预算不能简单相加作为每次实际延迟，但用于定位哪一层超标。

三、资源规划

本机 real 开发配置使用 32 GiB Colima 和 8 个 CPU，RAGFlow、Elasticsearch、MySQL、MinIO、
Valkey 与平台 MySQL 复用稳定容器，不为每个测试重建。业务 API 和 Worker 修改后单独重启。32 GiB
是本地联调资源上限的当前默认，不等于未来生产节点规格。

生产容量评估把业务 API/Worker 与 RAGFlow 数据节点分开观察。CPU 持续 70%、内存持续 75%、任务
积压超过 5 分钟或 P95 连续三个窗口超标时触发扩容评估。单次瞬时峰值不自动扩容，先排除异常批量
任务和供应商限流。

四、模型成本

模型成本按输入、输出和调用次数分别记录，不在前端展示 API Key 或业务空间地址。普通门店问答的
月度预算占模型总预算 55%，总部复杂分析占 25%，工作流与批量摘要占 15%，真实验收和故障演练预留
5%。预算比例是管理目标，不代表供应商计费折扣。

当月预测超过预算 80% 时通知模型治理负责人；超过 95% 时暂停新增批量任务，但不能中断正在进行的
高风险故障处置。禁止为了省费自动切换到用户没有创建或未获批准的模型。可选降级必须在模型管理
中预先配置，并在会话或员工界面明确显示。

五、缓存与上下文

知识检索结果只在租户和知识版本都一致时短期复用。模型回复默认不缓存，因为同一句问题可能受员工
提示、会话历史和模型版本影响。不得跨租户共享检索缓存。知识文档更新后，相关缓存必须按版本失效，
不能只依赖固定过期时间。

会话上下文达到模型限制前，平台可以做有来源的摘要，但摘要不能删除用户明确要求保留的约束。历史
正文继续在 MySQL 中保存；发送给模型的上下文只是执行快照。上下文缩减要记录发生过，但不记录受限
正文到普通日志。

六、压测与判定

容量验收必须从正式 HTTP/SSE 入口运行真实 API 和独立 Worker。分层压测可以定位数据库或模型适配
器瓶颈，但不能替代用户链路。压测问题使用专门知识库，不混入生产资料；结束后删除会话、员工、
工作流和知识库，保留聚合指标。

通过条件包括成功率至少 99.5%、无跨租户数据、无 OOM 或进程重启、任务积压在负载结束后 3 分钟内
清空、P95 满足对应问题类型预算。供应商明确限流时单独记录，不把重试后的成功掩盖为首次成功。

本计划的唯一检索标记是 CAP-SUMMIT-286。回答 120、48、30 三个数字时必须分别说明软配额、并发
会话和工作流配额，不能把它们当成同一个限制。
